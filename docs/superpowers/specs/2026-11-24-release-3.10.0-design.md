# Supabase Multi 3.10.0 Completion Design

## Intent

Finish the Backup & Restore release as a safe local control-plane feature: backups
can be verified and structurally validated without executing SQL; trusted full
backups can be tested only in a disposable, network-isolated Docker PostgreSQL
container; and remote restoration remains deliberately unavailable until its
destructive execution path has separate approval and end-to-end evidence.

## Goals

- Make validation reports distinguish integrity, structural validity, and tested
  restoreability.
- Make imported external backups explicit, safe, and available after dashboard
  refresh without copying SQL or changing the registry.
- Harden local restore reporting, cleanup, timeout handling, and inventory checks.
- Keep dashboard job progress phase-based and truthful.
- Publish consistent 3.10.0 version identity and practical, least-privilege docs.

## Non-goals

- No remote restore execution, cloud project creation, registry mutation, PAT
  rotation/revocation, production database operation, or secret output.
- No attempt to claim Storage objects or every Supabase platform setting are part
  of a PostgreSQL logical backup.

## Approaches

1. Enable remote SQL restore behind a UI confirmation. Rejected: confirmation
   cannot substitute for verified destination backup, permissions, compatibility,
   and production safeguards.
2. Keep restore code as an unstructured local utility. Rejected: it leaves the
   UI/MCP control-plane boundary and failure reports too weak for public release.
3. Keep remote execution disabled, expose read-only validation/planning through a
   whitelist, and strengthen the isolated local path. Selected: it meets the
   current safety evidence while preserving a future executor boundary.

## Architecture

`headless_control_plane.py` owns non-executing manifest validation and external
backup import records. `restore_engine.py` consumes only a fully validated full
backup, stages exact bytes, and runs a pinned image without network, ports, or
bind mounts. The local UI owns durable local job snapshots and presents reports;
the Runtime Bridge advertises only whitelist-based, non-destructive backup
operations. `runtime_identity.py` is the sole product-version source.

## Constraints

- All target selection is exact account + project + project ref; ambiguity fails.
- PAT values, passwords, SQL contents, and credential-bearing URLs never enter
  reports, API responses, documentation examples, or tests.
- Tests use synthetic fixtures or disposable Docker only; no real account or
  database is selected.
- Remote destructive restore remains absent from the advertised capability list.
