# Supabase Multi 3.10.0 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Ship a safe, documented Backup & Restore 3.10.0 release with verified local behaviour and no remote destructive executor.

**Architecture:** Validation remains non-executing and file-system bounded; local restore stages trusted bytes into a disposable Docker instance; UI and Runtime Bridge use the same control-plane APIs and capability whitelist. The remote path only inventories an exact, explicitly enabled non-production target.

**Tech Stack:** Python 3.11+, pytest, local HTTP UI, JavaScript, Docker CLI, Supabase CLI.

**Spec:** `docs/superpowers/specs/2026-11-24-release-3.10.0-design.md`

## Global Constraints

- Never expose or persist PAT/password/credential URL/SQL data.
- Resolve every target through registered account, project, and project ref.
- Restore execution is local-only and requires a trusted full backup plus a pinned digest.
- Remote restore execution is not advertised or implemented.
- Preserve legacy v1 backup manifests and do not require Full Access PATs.

## Review Focus

- An external path with a symlink, duplicate inventory entry, traversal, or changed byte must fail before SQL is touched.
- A job refresh or duplicate submission must preserve/report real phase state, never fabricate progress.
- A Docker/psql timeout or partial container creation must not leak diagnostics or leave a successful report.
- A target alias, production target, read-only target, or source-equals-destination must fail before network access.
- A bridge operation not on the whitelist must remain unavailable, including remote restore.
